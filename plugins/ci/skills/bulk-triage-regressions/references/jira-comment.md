# Existing-bug regression comment

## When to post

Use this as the only allowed comment template when adding regressions to an existing bug, whether creating a new triage or extending one. Respect the policy's write mode and comment enablement; this template does not authorize a write.

Post at most one comment per bug per run, covering all regressions added to that bug in the run. Before posting, read the bug's comments and skip the notice if the same triage and regression IDs are already listed. Keep the comment concise; put the full analysis in the duty report.

## Structure

Use the following Markdown structure. When posting through Jira REST, build the same structure in Atlassian Document Format (ADF), using explicit link marks for every reference: API-submitted plain text does not auto-link. Never leave a bare URL or issue key. Render the footer after a divider as its own marked block (an ADF `rule` followed by a `panel` of type `note`), and keep it last.

```markdown
**Component Readiness triage duty: <view>, <YYYY-MM-DD>**

Added <N> regression(s) to [triage <triage-id>](https://sippy-auth.dptools.openshift.org/sippy-ng/component_readiness/triages/<triage-id>) for this bug.

| Regression | Test | Variant |
|---|---|---|
| [<regression-id>](<test-details UI URL>) | `<full test name>` | <platform/network/topology/...> |

**Why it matches:** <one or two sentences: shared error signature and mechanism, and why it is this bug>.

**Evidence:** [<job-name>/<run-id>](<prow run URL>): `<one-line error excerpt>`

---

**AI-generated content:** This comment was generated by AI as part of Component Readiness triage duty. Please verify before acting on it.
```

## Field rules

- `<view>` and `<YYYY-MM-DD>` identify the run's Component Readiness view and date; `<N>` counts only the regressions added in this run. If the bug has multiple affected triages, repeat the linked triage sentence and its regression list within the same comment.
- Link every triage ID to its triage UI page, every regression ID to its test-details UI page, and every evidence run to its Prow page. Any additional issue or PR reference must also be clickable, using explicit ADF link marks when posting through REST.
- Convert each regression's `test_details_url` to the `sippy-ng` UI form, preserving its query parameters, as described in [API vs UI URLs under Pitfalls](../SKILL.md#pitfalls-learned-from-real-duty-runs). Never use the API URL in the comment.
- Use the full test name in inline code; never shorten it with `...`. Escape Markdown table delimiters in test names without dropping any text; use the exact name in ADF code-marked text. Describe the regression's platform/network/topology and other distinguishing variants.
- Use a table for two or more regressions. For a single regression, a one-line bullet is allowed: ``- [<regression-id>](<test-details UI URL>) — `<full test name>` — <platform/network/topology/...>``.
- Cite only 1–3 runs from the added regressions, each as a linked job/run ID with a short, one-line error excerpt. Keep long logs and the full analysis in the duty report. Do not include mentions.
- Use the footer shown above with its comment-specific wording, formatted like the parent skill's Phase 4 footer: a separate marked block after a divider (an ADF `rule` followed by a `panel` of type `note`), and leave it as the final block.
